# Coding standards

These standards apply to code generated by humans and agents.

## General standards

- Keep code simple, explicit, and testable.
- Prefer small modules with clear responsibilities.
- Do not add abstractions without a near-term use case.
- Avoid global mutable state.
- Avoid hidden network calls in constructors or config loading.
- Make errors actionable.

## Python standards

Use Python 3.11+.

### Typing

Use type hints for public functions and domain models.

Good:

```python
def load_source(path: Path) -> SourceSpec:
    ...
```

Avoid:

```python
def load_source(path):
    ...
```

### Pydantic

Use Pydantic v2 for manifest and domain validation.

- Keep validation close to the model.
- Prefer explicit `Literal` fields for known modes.
- Use useful error messages.
- Do not pass unvalidated dictionaries through the pipeline.

### Paths

Prefer `pathlib.Path` for filesystem work.

### Interfaces

Use `typing.Protocol` for pluggable boundaries such as:

- Source readers
- Parsers
- Extractors
- Entity resolvers
- Graph sinks

### Dependency policy

Before adding a dependency, check:

1. Is it required for the current issue?
2. Is it maintained?
3. Does it introduce heavy transitive dependencies?
4. Can it run locally without paid services?
5. Does it complicate packaging?

For v0.1, avoid heavy ML/LLM dependencies in the critical path.

## Core package boundaries

`packages/graphflow_core` should own:

- Manifest models
- Pipeline runner
- Source abstractions
- Parser abstractions
- Mapping logic
- Validation logic
- Graph object models
- Graph sink interfaces and implementations

Interface layers should not duplicate core behaviour.

## Error handling

Errors should explain:

- What failed
- Which manifest/file/field caused it
- How the user can fix it

Example:

```text
Invalid pipeline manifest: mapping.nodes[0].label references unknown ontology node label 'Organisation'. Known labels: Company, Person.
```

## Tests

Prefer fast unit tests for core logic.

Use integration tests only where useful, especially for Neo4j sink behaviour.

Tests should not require:

- Paid LLM APIs
- Cloud infrastructure
- External services except Dockerised local dependencies

## Formatting and linting

The exact tools may be finalised later. Likely choices:

- `ruff` for linting and formatting
- `pytest` for tests
- `mypy` or `pyright` later if type strictness becomes useful

## Frontend standards

When the web app is added:

- Keep UI thin over API endpoints.
- Avoid duplicating manifest validation logic in the browser.
- Prefer generated types from API schemas later.
- Keep the first UI demo simple: upload, configure, run, review, load.

## Documentation standards

Update docs when changing:

- Manifest shape
- Architecture
- CLI commands
- Local development flow
- Graph sink behaviour
- Extraction or entity-resolution semantics
